# Architecture

## Runtime components

- **React/Vite frontend** owns upload, progress polling, zone editing, playback, and presentation of API-derived results.
- **FastAPI** validates requests, coordinates background inference, exposes analysis/history routes, and sanitizes client-facing errors.
- **Video processing** validates decoded metadata with OpenCV and iterates frames without loading the full video into memory.
- **Detector** wraps configurable Ultralytics inference and writes newline-delimited structured detection records plus an annotated MP4.
- **Event engine** groups detections from the same sampled frame and class into reproducible `object_detected` events. It assigns a zone using the bounding-box centroid when a configured normalized polygon contains it.
- **Analytics** derives time buckets and zone summaries from stored detection/event records.
- **SQLite repository** owns session, event, and aggregate persistence behind a repository boundary.
- **Prediction services** analyze only compatible completed sessions and return explicit insufficient-data responses when validation cannot be performed.

## Data path

```text
Uploaded file → metadata validation → session row → background detector
  → detection JSONL → events JSONL → temporal and spatial summaries
  → atomic SQLite completion transaction → API → dashboard
                                         └→ patterns → evaluated forecast → advisory support

Browser camera → sampled JPEG over WebSocket → shared detector → live observations/overlay
```

The frame record is the lowest-level stored observation. Events group same-frame class observations; temporal and spatial aggregates summarize those observations. Uploaded temporal analytics separately compare average detector instances per sampled frame against a configurable trailing median/scaled-MAD activity baseline. Only consecutive observed buckets are compared; gaps reset the baseline. The signal is detector-output volume, not occupancy, an incident determination, or a forecast, and it has not been validated against labeled activity anomalies. Forecasts are distinct from observations and expose their target, supporting sessions, model configuration, and rolling-origin evaluation.

The upload-analysis UI sends one status request at a time and schedules the next request only after the previous response completes. Transient status failures use exponential backoff and stop after five failures; the operator can reconnect to the existing job without starting duplicate inference. Poll timers and in-flight requests are canceled when the analysis view unmounts.

`GET /api/health` includes best-effort process telemetry from Python resource counters. CPU percentage is the process CPU-time delta between successive health calls normalized to one core (so multithreaded work can exceed 100%); the first sample is unavailable. Resident memory is the process peak since startup, not a current working-set measurement. If the configured device is MPS and PyTorch exposes the counter, allocated tensor memory is included, not total device utilization. These measurements are displayed with their limits and do not fabricate utilization when a counter is unavailable.

## Persistence and lifecycle

The default database is `backend/data/predix.sqlite3`. Source videos live in `backend/uploads/`; annotated videos and intermediate JSONL artifacts live in `backend/analysis_outputs/`. These paths are ignored by Git. Deleting a session removes its files and cascades through SQLite records. Zone configuration is stored per video before analysis starts.

Job state is held in memory and one analysis job is allowed at a time per process. SQLite history survives process restart, but active jobs do not. Multi-worker job coordination is not implemented.

## Live source and streaming lifecycle

Uploaded video, browser camera, browser-native HTTPS HLS, and allowlisted RTSP frames share the detector runtime, `process_frame` detection-and-tracking boundary, and single-pipeline reservation; input sources do not create a second inference stack. The browser requests camera permission only after the user starts a session, downsamples camera/HLS frames, and sends one JPEG at a time over `/api/live/ws`. Native HLS playback is available only when `canPlayType` reports support; it requires an HTTPS `.m3u8` URL and anonymous CORS permission for canvas sampling. The playlist and its referenced resources are fetched directly by the operator's browser, not the backend, so nested playlist hosts cannot bypass backend host controls. The Live Camera view accepts an RTSP URL whose exact hostname is in `RTSP_ALLOWED_HOSTS`; it sends `start_rtsp` and requests samples with `next_frame`. FFmpeg open/read waits have configured timeouts. RTSP URL credentials are not returned or persisted, and the sampled preview frame is sent only to the connected operator and is not stored. This path requires a trusted network because API authentication is not implemented. Each live session uses a short-lived greedy IoU tracker to associate same-class boxes on every inferred frame; its IoU threshold and missed-sample retention are configurable with `TRACK_IOU_THRESHOLD` and `TRACK_MAX_MISSED_FRAMES`. Upload inference cadence follows `FRAME_STRIDE`; browser live cadence follows the frontend live interval. Occupancy counts active person tracks, including tracks retained through the configured missed-sample limit; current raw person detections, observed tracks, and carried tracks are reported separately. In zones, a carried track remains in its last observed zone until it is observed elsewhere or expires. This brief smoothing can temporarily overcount a person who left during a missed sample, and the estimate can still miss or double-count under occlusion, camera motion, track fragmentation, or detector error. Counts are not unique-person totals. Live observations expose anonymous temporary track IDs, session-relative dwell time, and image-space pixel displacement; displacement is not calibrated physical movement. Track state and live frames remain in memory and are cleared on disconnect. Browser camera, RTSP, and HLS source resources are released on stop or unmount; both RTSP and HLS retries are bounded. Do not pass RTSP URLs to an HTML `<video>` element.

When the owning upload or live pipeline finishes, the runtime drops its cached detector model and attempts to clear the selected MPS/CUDA cache before releasing the pipeline reservation. This bounds idle inference-memory retention; the next session lazily reloads the model. A release from a non-owning source cannot unload or release an active pipeline.

Operators may draw normalized polygon zones over the live preview and optionally set capacity. Configuration is validated with the same zone schema as uploaded video and sent over the WebSocket; estimates count temporary person tracks by bounding-box center. For continuing tracks, live observations count changes between zone memberships and retain aggregate entry/exit totals and zone-to-zone counts during the session. Zone configuration, short trend history, and track membership state are discarded on disconnect; aggregate session metrics, including final zone totals and any computed occupancy deviation/early-warning evidence, are persisted. Capacity statuses use the shared ordered thresholds. When six baseline samples and a current sample are available, occupancy deviations use the configured median/scaled-MAD rule; the early-warning cue requires both this deviation and configured HIGH/CRITICAL capacity. Missing or incomplete evidence remains `insufficient_data`, rather than being interpreted as no combined signal. A per-zone security-attention advisory exposes capacity/deviation triggers for human review only; it does not prescribe staffing or allocate resources. The Live Camera view and uploaded-session Digital Twin surface zones with review cues ordered by configured rule category; this is not an incident-risk ranking. These rules have not been evaluated against labeled anomaly/incident outcomes. Observed transitions can miss movement during detection gaps, and this feature does not create suspicious-object security alerts.

Live and uploaded zone trend text summarizes the net change between the first and last valid samples in the displayed window and reports the observed estimates-per-minute rate only when elapsed time is positive. This rate is descriptive, can be noisy when the window is short, and is not a forecast or an alert threshold.

The live WebSocket groups current HIGH/CRITICAL capacity and occupancy-deviation signals into at most one `occupancy_alerts` item per zone. The stable per-zone key prevents repeated samples from creating duplicate alerts; later observations update the snapshot. `GET /api/live/alerts` returns the current snapshot only while streaming, and the stopped session retains its last snapshot in the aggregate history summary. Alert severity follows operator-configured capacity status, confidence is not applicable, and these records do not identify incidents or suspicious objects.

Live zone prediction uses the same validated chronological trailing-mean-versus-persistence forecaster as uploaded sessions. A session-local aggregator forms 15-second means from sampled track-aware visible-person estimates and retains at most 240 completed buckets per zone (the one-hour maximum horizon). It requires three training plus three validation windows per horizon: six continuous minutes for one minute ahead, 30 minutes for five minutes, and 60 minutes for ten minutes. Missing buckets remain missing; the forecaster returns insufficient data instead of imputing zero. The current partial bucket is not forecast input. Model choice, validation metrics, supporting-bucket count, MAE uncertainty, and session-relative as-of time accompany each forecast. These within-session results are not guaranteed to generalize to another session or camera.

SQLite initialization records schema version 4 in `PRAGMA user_version` and is idempotent. Version 2 adds indexed `occupancy_observations` rows for track-aware zone buckets. Version 3 adds `live_sessions` for aggregate browser-camera session history; startup marks live rows without an end time as interrupted. Version 4 adds indexed per-zone live occupancy buckets and available, chronologically evaluated crowd predictions. Upgrades preserve uploaded-video sessions and history and do not fabricate measurements for legacy sessions. Live history stores aggregate counts and estimates only, never sampled frames or temporary track IDs. Operators can query per-zone occupancy history and delete a live session through the API; deletion cascades to its bucket and prediction rows. Future schema changes must add explicit forward migration steps and regression coverage.

Uploaded-video zone occupancy is estimated from distinct temporary person track IDs in each sampled frame, assigned by normalized bounding-box center to the existing polygon. Zones can optionally set a capacity and ordered LOW/MODERATE/HIGH/CRITICAL ratios; defaults are 50%, 75%, 90%, and 100%, and the editor allows configuring them. Without complete tracking, a valid polygon, or an explicit capacity, occupancy or capacity status remains unavailable/unconfigured rather than inferring it from raw detection instances.

Spatial analytics also compare each continuing person's observed zone membership between analyzed frames to summarize observed entries, exits, and direct zone-to-zone changes. The analytics retain only aggregate counts, not track IDs. These counts exclude unobserved departures and can miss transitions when inference skips frames or tracks fragment; clips with incomplete tracking report transition estimates as unavailable.

Uploaded and live zone summaries include a `security_attention` advisory when track-aware occupancy and operator-configured capacity are available. It reports the configured capacity/deviation signals and recommends human review; it does not calculate a risk score, establish safety, prescribe staffing, or allocate resources. Its rules have not been evaluated against labeled incident outcomes.

## Trust boundaries and limitations

Uploads are untrusted input: extension, MIME, size, and actual decodability are checked; server paths are generated from UUIDs. CORS uses configured origins. The application has no user authentication or authorization and should remain on a trusted host/network or behind an authenticated gateway. SQLite is appropriate for local academic use; concurrent distributed deployment needs a different job coordinator and database deployment plan.
